# Day 05 - terraform.tfstate: State vs. Reality

## Overview

Day 4 built a highly available web server - an Auto Scaling Group behind an
Application Load Balancer. Day 5 doesn't add new infrastructure; it pokes at
the file Terraform quietly created the first time that infrastructure was
applied: `terraform.tfstate`. The question for the day was simple - what
actually happens if this file and the real infrastructure it describes stop
agreeing with each other?

## Files

```
Day-05/
├── main.tf              - provider, default VPC data sources, security groups,
│                           ALB + target group + listener, launch template,
│                           ASG, ASG-to-target-group attachment
├── variables.tf          - region, instance_type, min_size, max_size, desired_capacity
├── outputs.tf             - alb_dns_name, target_group_arn, asg_name
└── README.md              - this file / learning journal
```

`terraform.tfstate` and `terraform.tfstate.backup` are generated by
`terraform apply` and are git-ignored (see repo root `.gitignore`) - they're
a local record of what Terraform built, not source code.

## Architecture

Same shape as Day 4's clustered build: internet gateway → ALB (public,
`alb_sg` open on port 80) → target group → Auto Scaling Group of instances
in `instance_sg`, which only trusts traffic from the ALB. Nothing new was
deployed today - this setup was the test subject for the state file
experiments below.

## How to Run

```bash
cd Day-05
terraform init
terraform plan
terraform apply
```

Wait for instances to pass health checks, then hit the `alb_dns_name`
output over plain HTTP. Once you've reproduced the experiments in the
learning journal below:

```bash
terraform destroy
```

## Learning Journal

### The File That Pretends to Be Your Infrastructure

`terraform.tfstate` is Terraform's memory - a JSON record of every resource
it has actually created, born the moment `terraform apply` first talks to
AWS and gets back real IDs and ARNs to remember. Nobody hand-writes it and
no project starts with one.

The part that trips people up: **the state file is not the infrastructure,
it's a description of it.** Think of it like a cargo ship's manifest. If
someone back at the office deletes container 47 from the spreadsheet, the
container doesn't vanish from the ship - it's still out there, indifferent
to the paperwork. The manifest changed; the ship didn't.

### Test 1 - Editing the State File Directly

I opened `terraform.tfstate` for this setup and renamed one of the resources
directly inside the JSON, then ran `terraform plan`.

**Result:** no changes detected. The renamed resource still exists in AWS
exactly as before - all I did was make Terraform's notes wrong. The ALB kept
serving traffic, completely unaware that its own state file now disagreed
with itself.

### Test 2 - Editing the Console Instead

This time I went into the AWS console, found the resource, and renamed one
of its tags there instead of in the file.

**Result:** something real changed - the live resource's tag genuinely
updated in AWS, right now, for real. But `terraform.tfstate` still said the
tag was whatever the `.tf` files originally declared. That gap between what
Terraform *believes* is true and what is *actually* true is called **drift**.

Running `terraform plan` afterward caught it immediately: Terraform calls
the AWS API, pulls the live state of the resource, and diffs it line by line
against the `.tf` config and the last-known state. The mismatch showed up as
a planned change to bring the tag back in line.

This is the underlying rule: **AWS is authoritative over itself; the state
file's only job is to keep an accurate mental model of it.** Editing the
file changes the model without touching reality. Editing the console changes
reality without touching the model. Either way you get a mismatch - but only
one of them is `terraform plan` guaranteed to catch.

### Test 3 - The Blind Spot

I tried the same trick on an individual EC2 instance inside the Auto Scaling
Group - renamed it in the console, expecting `terraform plan` to flag it the
same way it flagged the ALB tag.

**Result:** nothing. Not a bug - a deliberate blind spot. `terraform.tfstate`
only tracks resources actually declared in the `.tf` files. This config
declares `aws_autoscaling_group.example` and `aws_launch_template.example` -
those are what's written into state and watched. The individual instances
are something the ASG creates, replaces, and scales entirely on its own;
Terraform has a ledger entry for the ASG, but none for instance `i-0abc123`
specifically, so it has nothing to compare the rename against.

Something real still changed - just not something Terraform ever promised to
watch. Drift detection only works on what's written into state; anything
delegated to another service to manage on its own (like an ASG managing its
fleet) is a place changes can happen invisibly.

### Conclusion

`terraform.tfstate` is not the infrastructure - it's the story Terraform
tells itself about the infrastructure, rewritten after every `apply` and
consulted before every `plan`. Edit the story by hand and the real world
doesn't notice. Edit the real world through the console and the story stays
wrong until the next `plan` forces Terraform to go check. And whatever
Terraform never declared in the first place, it will never check at all.

### Challenges and Fixes

- If `terraform plan` shows no drift after a console edit: confirm you
  edited an attribute Terraform actually manages (e.g. a tag set in
  `main.tf`), not one AWS sets independently.
- If you can't find the instance IDs in the ASG to test the blind spot:
  `aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names example-asg`
  lists the current instances.
